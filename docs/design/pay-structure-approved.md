# Pay Structure — approved conversational setup with manual review

Approved after the user clarified that description in any language is the preferred first-time setup and should remain accessible in Profile. First-time: describe pay -> optional brief AI clarification -> editable review of structured fields with deterministic worked example -> confirm -> persist configuration and pay-period anchor -> completion beat -> guided walkthrough. Manual setup free and accessible from description. Profile: show current arrangement, Describe a change or Edit manually; both converge on the same editable review, and persist only on confirmation.

The AI callable accepts plain text; raw rate-sheet photo/PDF uploads are removed from this UI because the existing endpoint explicitly rejects them. User sees a clear text/manual option. DeepSeek's supported text model is server-side. The callable enforces auth, a 20-request/day user cap and a concurrent lock. It never writes pay settings; it maps into an allowlisted model and asks questions for missing main rate, percentage fee, tier/grid, currency or basis instead of guessing. Missing amounts never become £0 by default; user explicitly confirms a zero contractor fee. Current config sent when describing a change is a known structured arrangement, not a source of authority over provider instructions. User input and AI response are not persisted in Stop Tracker or analytics. The processor receives the submitted description and any prior answer; do not claim it deletes that data.

The review form supports all six existing pay models: flat per stop, day rate, hourly, per mile with optional base, marginal stop tiers, and current nearest-band stop/mileage grid. The selected model exposes its required fields; there is no Advanced disclosure for flat per-stop pay. Excess parcel pay and contractor percentage are separate optional controls. A percentage applies to all gross work earnings (including extras) before business expenses; fixed charges stay in Expenses. Validation rejects omitted rates, malformed or overlapping tiers, incomplete grids, and percentages outside 0–100. Preview derives from shared deterministic calculation code and is labelled example only, before expenses/tax; no AI arithmetic or AI on every keystroke.

Version history: every confirmed change stores a structured config with new version id and savedAt. Transaction writes the current config and history together; guest localStorage rollback preserves both if one write fails. A pre-version config is kept as `legacy` on first change. Saved Quick Entry records already retain the exact payStructureSnapshot, so previous totals are never repriced. When adding a new missed-day entry, a focused choice lists current and saved versions and requires the user to select applicable rates before entry. The app does not infer a historical effective date from a save timestamp. Existing entries keep their stored snapshot. Data version changes appear in Home/Quick Entry after context adoption.

States: first-time blank manual structure; AI clarification and review; returning current arrangement; disabled repeated save; errors retain draft; onboarding completion only after persistence. Guest local status, signed-in offline rejection, refresh conflict error for a newer setting saved on another device. A missing setup blocks new Quick Entry instead of using an example DPD rate. Guest descriptions remain in transient component state only. Analytics allowlisted setup events without language text, rate values, fees or contractor names.

Mobile form uses native date/select/decimal inputs, 16px+ type, touch targets, safe-area sticky footer, reduced-motion changes and confirmation on exit with a changed draft. Desktop width is constrained; grid rates scroll horizontally with labels and keyboard access. iOS Safari, Android Chrome, PWA and Capacitor still require manual device QA. The Firebase function deployment and real multilingual provider/secret test are required before live AI setup can be claimed. A dedicated security audit remains a launch gate.
